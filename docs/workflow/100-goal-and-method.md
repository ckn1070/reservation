# 목표와 방법 협업 원칙

이 문서는 사용자의 요청을 어떻게 해석하고, 목표 달성 방법을 어떻게 선택할지 정의합니다.

## 목적

- 사용자가 제시한 내용을 단순 실행 지시가 아니라 목표와 아이디어로 다룹니다.
- 목표를 더 잘 달성할 수 있는 방법이 있으면 먼저 제안하고 논의합니다.
- 작업자가 임의로 과도하게 변경하지 않으면서도 더 나은 선택지를 놓치지 않게 합니다.

## 핵심 원칙

- 사용자가 제시하는 것은 기본적으로 달성하고 싶은 목표입니다.
- 사용자가 함께 제시하는 방식은 절대적으로 따라야 하는 명령이 아니라 하나의 아이디어로 해석합니다.
- 작업자는 목표를 기준으로 사용자의 아이디어를 평가합니다.
- 더 나은 대안이 있으면 구현 전에 먼저 제안합니다.
- 대안이 사소하거나 결과에 큰 차이가 없으면 기존 코드와 문서 규칙에 맞춰 진행합니다.
- 최종 방식은 논의를 통해 정하되, 작업자는 기술적 위험과 유지보수 비용을 명확히 드러냅니다.

## 작업 절차

1. 사용자의 요청에서 목표를 분리합니다.
2. 사용자가 제시한 방법, 제약, 선호를 구분합니다.
3. 기존 코드, 문서, 프로젝트 관례를 확인합니다.
4. 제시된 방법이 목표 달성에 적절한지 검토합니다.
5. 더 나은 대안이 있으면 장단점과 함께 제안합니다.
6. 합의된 방향 또는 명백히 적절한 방향으로 작업합니다.
7. 완료 후 어떤 판단으로 진행했는지 간단히 보고합니다.

## 먼저 제안해야 하는 경우

- 구조나 책임 경계를 바꾸는 변경입니다.
- 이후 작업 방식이나 문서 체계에 영향을 주는 변경입니다.
- 데이터 손실, 보안, 인증, 권한, 마이그레이션과 관련된 변경입니다.
- 구현 방식에 따라 유지보수 비용이 크게 달라지는 변경입니다.
- 사용자의 아이디어보다 명확히 더 단순하거나 안전한 방법이 있습니다.
- 요청 의도는 이해했지만 구체적인 목표가 불명확합니다.

## 바로 진행해도 되는 경우

- 문서 오탈자 수정처럼 영향 범위가 작습니다.
- 기존 패턴이 명확하고 선택지가 사실상 정해져 있습니다.
- 대안 간 차이가 작고 결과물에 의미 있는 영향을 주지 않습니다.
- 사용자가 이미 명확히 합의된 규칙 안의 작업을 요청했습니다.

## 대안 제안 형식

대안을 제안할 때는 다음 내용을 간결하게 포함합니다.

- 이해한 목표
- 사용자가 제시한 아이디어
- 해당 아이디어의 장점과 리스크
- 추천하는 대안
- 사용자가 결정해야 하는 지점
