# 개발 작업 워크플로우

이 문서는 개발 작업을 진행할 때의 기본 절차를 정의합니다.

## 목적

- 코드 변경 전에 필요한 맥락을 확인합니다.
- 변경 범위를 목표에 맞게 유지합니다.
- 기능 추가, 버그 수정, 도메인 로직 변경은 TDD를 기본 방식으로 진행합니다.
- 구현 후 검증과 보고가 누락되지 않게 합니다.

## 기본 절차

1. 요청의 목표와 제약을 확인합니다.
2. 관련 문서와 코드를 읽습니다.
3. 기존 구조와 관례를 기준으로 구현 방식을 정합니다.
4. 필요한 경우 더 나은 대안을 먼저 제안합니다.
5. 영향이 큰 설계 작업이면 `110-design-workflow.md`를 적용합니다.
6. 아키텍처와 기술 스택 Best Practice 적용 여부를 확인합니다.
7. TDD 적용 여부를 판단하고, 적용이 어려우면 이유와 대안을 제시합니다.
8. 변경 범위를 작게 유지하면서 구현합니다.
9. 가장 관련성 높은 검증을 실행합니다.
10. 변경 내용, 검증 결과, 남은 리스크를 보고합니다.

## 구현 전 체크리스트

- 목표와 사용자가 제시한 아이디어를 구분했습니다.
- 관련 `000-index.md`와 필요한 상세 문서를 확인했습니다.
- 기존 코드의 책임 경계와 스타일을 확인했습니다.
- 변경 범위가 현재 목표에 필요한 수준인지 확인했습니다.
- 아키텍처, 도메인 모델, DB 스키마, 기술 선택에 큰 영향을 주는 작업인지 확인했습니다.
- Clean Architecture와 기술 스택 문서에서 적용할 기준을 확인했습니다.
- TDD로 진행할 수 있는 작업인지 확인했습니다.
- 사용자나 다른 작업자가 만든 기존 변경 사항을 되돌리지 않는지 확인했습니다.

## 구현 원칙

- 기존 코드 스타일과 프로젝트 구조를 우선 따릅니다.
- 새 추상화는 실제 중복이나 복잡도를 줄일 때만 추가합니다.
- 임시방편보다 원인을 해결합니다.
- 관련 없는 리팩터링은 하지 않습니다.
- 파일 이동, 이름 변경, 대규모 포맷 변경은 필요한 경우에만 수행합니다.
- 보안, 인증, 데이터 변경은 더 보수적으로 검토합니다.

## TDD 기준

- 기능 추가, 버그 수정, 도메인 로직 변경은 `210-tdd-workflow.md`를 따릅니다.
- 먼저 실패하는 테스트를 작성하고, 실패 이유를 확인한 뒤 구현합니다.
- TDD가 어렵다면 구현 전에 이유와 대안을 사용자에게 제시합니다.
- TDD 예외 작업도 적절한 검증 명령이나 수동 확인 기준을 남깁니다.

## 아키텍처와 기술 스택 기준

- 영향이 큰 설계 작업은 `110-design-workflow.md`를 먼저 적용합니다.
- 대부분의 코드 작업은 `../architecture/000-index.md`를 기준으로 Clean Architecture 적용 가능성을 확인합니다.
- 기술 선택과 프레임워크 사용은 `../tech-stack/000-index.md`에서 관련 문서를 확인합니다.
- 명확한 Best Practice가 있으면 기본값으로 적용합니다.
- 프로젝트 제약이나 트레이드오프가 있으면 선택지와 우위를 사용자에게 제시합니다.

## 검증 기준

- 변경한 코드에 가장 가까운 테스트를 먼저 실행합니다.
- 관련 테스트가 명확하지 않으면 프로젝트의 기본 테스트 명령을 확인합니다.
- 이 프로젝트의 기본 테스트 후보는 `./mvnw test`입니다.
- 테스트를 실행하지 못했거나 실행하지 않는 편이 적절하면 완료 보고에 이유를 남깁니다.

## 완료 보고 기준

- 어떤 목표를 기준으로 작업했는지 설명합니다.
- 핵심 변경 내용을 짧게 요약합니다.
- 변경한 파일을 명시합니다.
- 실행한 검증 명령과 결과를 적습니다.
- 남은 리스크나 후속으로 정리할 내용을 숨기지 않습니다.
