# 설계 워크플로우

이 문서는 아키텍처, 도메인 모델, 모듈 경계, DB 스키마, 기술 선택처럼 장기 유지보수성과 확장성에 큰 영향을 주는 설계 작업의 진행 기준을 정의합니다.

## 목적

- 설계를 단순한 구조 제안이 아니라 제품 목표, 도메인 특성, 운영 리스크를 반영한 의사결정으로 다룹니다.
- 현대 개발론과 검증된 Best Practice를 출발점으로 삼되, reservation 맥락에 맞게 장단점과 트레이드오프를 비교합니다.
- 기존 문서나 초기 가정에 갇히지 않고 더 완결성 높은 설계를 우선합니다.
- 선택한 설계의 리스크, 재검토 조건, 후속 검증 방법을 명확히 남깁니다.

## 적용 범위

다음 작업은 설계 워크플로우를 우선 적용합니다.

- 패키지 구조, 모듈 경계, 계층 구조 결정
- 도메인 모델링과 일관성 경계 결정
- DB 스키마, 주요 제약조건, 데이터 생명주기 설계
- 인증, 인가, 사용자 권한, 관리자 권한 구조
- 결제, 알림, 대기열, 외부 시스템, 파일 저장소, 검색엔진, 메시징, 캐시 연동 방식
- 이벤트, 비동기 처리, 배치 작업, 스케줄러 도입
- 성능, 보안, 데이터 무결성, 운영 안정성에 큰 영향을 주는 기술 선택
- 이후 되돌리기 어렵거나 migration 비용이 큰 결정

다음 작업은 설계 워크플로우를 가볍게 적용하거나 생략할 수 있습니다.

- 오탈자 수정
- 문서 표현 정리
- 기존 합의가 명확한 작은 구현
- 영향 범위가 작은 설정 변경
- 설계를 확정하기 전 기술 가능성을 확인하는 짧은 spike

## 핵심 원칙

- 설계의 최우선 목표는 완결성 높은 판단입니다.
- 사용자의 요청은 구현 지시보다 달성하려는 목표와 문제 상황으로 먼저 해석합니다.
- 기존 문서는 현재까지의 합의와 맥락이지 정답이 아닙니다.
- 더 나은 설계를 위해 필요하면 기존 문서도 수정 대상으로 봅니다.
- Best Practice는 결론이 아니라 후보군을 좁히는 출발점입니다.
- 영향이 큰 설계 결정은 최소 2개 이상의 대안을 비교합니다.
- 설계 리스크는 숨기거나 나중 문제로 미루지 않습니다.
- 문제를 알고 감수하는 것과 문제를 모르고 마주하는 것은 다르므로, 감수할 리스크를 명시합니다.
- 설계자가 할 수 없는 검증이나 판단이 있으면 그 이유와 필요한 추가 정보를 명확히 제시합니다.

## 설계 절차

1. 사용자의 제품 목표, 현재 단계, 장기 확장 가능성을 정리합니다.
2. 사용자가 제시한 구현 아이디어, 제약, 선호를 목표와 분리합니다.
3. 관련 `000-index.md`, 기존 코드, 기존 문서, 프로젝트 관례를 확인합니다.
4. 기존 문서의 기준이 현재 목표에 적합한지 재검토합니다.
5. 관련 Best Practice, 공식 문서, 널리 검증된 아키텍처 패턴을 확인합니다.
6. 아직 모르는 것, 가정한 것, 결정에 영향을 주는 불확실성을 적습니다.
7. 가능한 선택지를 2~3개로 압축합니다.
8. 평가 축을 기준으로 대안을 비교합니다.
9. 선택한 설계안과 선택하지 않은 대안의 이유를 설명합니다.
10. 설계 검증 절차를 수행합니다.
11. 감수할 트레이드오프와 재검토 조건을 남깁니다.
12. 필요한 문서 수정, 작업 문서 작성, 구현 전 확인 사항을 정리합니다.

## 평가 축

설계 대안은 다음 축을 기준으로 비교합니다.

- 기술적 완결성: 책임 분리, 의존성 방향, 오류 처리, 일관성이 명확한가.
- 유지보수성: 변경 영향 범위가 작고 새 작업자가 구조를 추론하기 쉬운가.
- 확장성: 기능, 데이터, 외부 시스템, 운영 규모가 늘어날 때 구조가 버티는가.
- 테스트 가능성: 핵심 정책을 빠르고 안정적인 테스트로 검증할 수 있는가.
- 성능: 예상 병목, 조회 패턴, 데이터 증가에 대한 대응이 가능한가.
- 데이터 무결성: 제약조건, 트랜잭션, 상태 전이가 안전한가.
- 보안: 인증, 인가, 입력 검증, 민감정보, 감사 로그 기준이 명확한가.
- 운영 안정성: 장애 분석, 로그, 모니터링, 배포, migration 리스크가 관리되는가.
- 개발 속도: 현재 단계에서 구조화 비용이 목표 달성을 방해하지 않는가.
- 되돌리기 비용: 선택이 틀렸을 때 변경하거나 migration하기 쉬운가.
- 프로젝트 현실성: 인력, 시간, 운영 역량에 비해 과하지 않은가.

## 설계 검증 절차

설계안은 결정 전에 다음 절차로 검증합니다.

### 목표 적합성 검증

- 설계가 제품 목표를 직접 지원하는지 확인합니다.
- 현재 구현 범위와 장기 확장 가능성을 구분합니다.
- 지금 필요한 구조와 나중에 열어둘 확장 지점을 분리합니다.
- 설계가 기술적 취향이 아니라 실제 문제를 해결하는지 확인합니다.

### 경계 검증

- 모듈, 계층, 도메인 경계가 업무 언어와 맞는지 확인합니다.
- 다른 모듈의 내부 구현이나 DB 테이블을 직접 건드리는 흐름이 있는지 확인합니다.
- 의존성 방향이 문서화된 아키텍처 원칙과 충돌하는지 확인합니다.
- 경계가 너무 크거나 작아 변경 단위가 흐려지는지 확인합니다.

### 데이터 검증

- 핵심 Entity, 값 객체, 상태값의 생명주기를 확인합니다.
- 반드시 지켜야 하는 불변조건을 도메인 규칙과 DB 제약조건 중 어디에 둘지 결정합니다.
- 생성, 수정, 삭제, 숨김, 이력화, 복구, 감사 로그가 필요한 데이터를 구분합니다.
- 데이터 증가, 검색, 정렬, 페이징, 인덱스 전략이 필요한 지점을 확인합니다.

### 시나리오 검증

- 정상 흐름만이 아니라 실패, 권한 부족, 동시성, 중복 요청, 외부 시스템 장애를 포함합니다.
- 핵심 유스케이스 2~3개를 선택해 설계가 실제 코드 흐름으로 자연스럽게 이어지는지 확인합니다.
- 읽기 흐름과 쓰기 흐름을 분리해 각각의 모델과 성능 요구를 검토합니다.
- 도메인 규칙이 Controller, Entity, Mapper, 외부 Adapter에 흩어지지 않는지 확인합니다.

### 구현 가능성 검증

- 선택한 설계가 실제 패키지, 클래스, 인터페이스, 테이블 구조로 자연스럽게 표현되는지 확인합니다.
- 핵심 유스케이스 하나를 기준으로 요청부터 저장소까지의 흐름을 간단히 스케치합니다.
- 설계가 과도한 매핑, 빈 추상화, 불필요한 순환 참조를 만들지 않는지 확인합니다.
- 구현자가 설계를 보고 첫 작업 단위를 명확히 잡을 수 있는지 확인합니다.

### 품질 속성 검증

- 성능, 보안, 확장성, 운영 안정성 같은 품질 속성을 구체적인 시나리오로 표현합니다.
- 예측만으로 판단하지 않고, 측정이나 spike가 필요한 항목을 분리합니다.
- 병목이 예상되는 지점과 실제로 측정해야 하는 지점을 구분합니다.
- 장애가 발생했을 때 사용자 영향과 복구 방법을 검토합니다.

### 테스트 가능성 검증

- 도메인 규칙과 유스케이스를 Spring Context 없이 테스트할 수 있는지 확인합니다.
- Web, Persistence, Security Adapter는 slice 또는 integration test로 검증 가능한지 확인합니다.
- 설계가 TDD 흐름을 방해할 정도로 느린 테스트만 강제하지 않는지 확인합니다.
- fake, fixture, test data 전략이 필요한 지점을 표시합니다.

### 보안과 권한 검증

- 인증된 사용자, 미인증 사용자, 권한 부족 사용자, 관리자 권한을 구분합니다.
- 사용자 입력, 외부 URL, 검색어, 정렬 조건의 검증 위치를 정합니다.
- 민감정보 저장, 노출, 로그 출력, 마스킹 기준을 확인합니다.
- 관리자 기능은 감사 로그와 권한 경계를 함께 검토합니다.

### 운영과 변경 검증

- 설정, profile, secret, migration, 배포 환경 차이를 고려합니다.
- migration 실패, 롤백, 데이터 보정이 필요한 경우를 검토합니다.
- 로그, 메트릭, 알림, 추적이 필요한 핵심 흐름을 표시합니다.
- 선택한 설계가 틀렸을 때 되돌리거나 단계적으로 바꾸는 경로를 설명합니다.

### 반례 검증

- 선택한 설계가 실패할 수 있는 조건을 의도적으로 찾습니다.
- 사용량, 데이터량, 기능 수, 외부 연동 수가 늘어났을 때 깨지는 지점을 검토합니다.
- 선택하지 않은 대안이 더 좋아지는 조건을 확인합니다.
- 선호하는 방향을 정당화하기 위해 리스크를 축소하고 있지 않은지 점검합니다.

### 문서 동기화 검증

- 선택한 설계가 기존 문서와 충돌하는지 확인합니다.
- 충돌한다면 기존 문서를 따를지, 기존 문서를 수정할지 명확히 결정합니다.
- 문서 수정이 필요한 경우 수정 대상과 이유를 설계 산출물에 포함합니다.
- 설계 결정이 반복적으로 참조될 가능성이 높으면 작업 문서 또는 별도 결정 기록 작성 여부를 검토합니다.

## 설계 중단 조건

다음 경우에는 설계를 확정하지 않고 사용자에게 확인합니다.

- 사용자의 제품 목표나 우선순위가 불명확합니다.
- 도메인 경계가 불명확하고 대안의 비용 차이가 큽니다.
- 대안의 장단점이 비슷해 기술적 판단만으로 결정하기 어렵습니다.
- 보안, 데이터 무결성, 운영 비용, 법적 리스크가 걸려 있습니다.
- 기존 문서와 더 나은 설계 방향이 충돌합니다.
- 필요한 Best Practice나 공식 문서 확인을 할 수 없습니다.
- 설계 검증에 필요한 코드, 데이터, 운영 환경 정보를 확인할 수 없습니다.

중단 시에는 단순히 질문만 하지 않습니다.
현재까지 확인한 사실, 가능한 선택지, 결정에 필요한 정보를 함께 제시합니다.

## 설계 답변 형식

설계 제안은 기본적으로 다음 형식을 사용합니다.

```md
## 이해한 목표

## 핵심 제약과 가정

## 관련 Best Practice

## 선택지

| 선택지 | 장점 | 단점 | 적합한 경우 |
| --- | --- | --- | --- |
| A | | | |
| B | | | |

## 추천안

## 이유

## 감수할 트레이드오프

## 주요 리스크

## 검증 결과

## 이 선택이 틀릴 수 있는 조건

## 재검토 조건

## 구현 전 확인 사항
```

작은 설계는 형식을 축약할 수 있습니다.
다만 영향이 큰 설계에서 대안, 리스크, 재검토 조건을 생략하지 않습니다.

## 산출물 기준

설계가 완료되려면 다음 항목이 남아야 합니다.

- 이해한 목표
- 주요 가정과 불확실성
- 비교한 대안
- 선택한 설계안
- 선택하지 않은 대안과 이유
- 감수하기로 한 트레이드오프
- 주요 리스크
- 설계 검증 결과
- 재검토 조건
- 필요한 문서 수정 목록
- 구현으로 넘어가기 전 확인 사항
- 구현 후 확인해야 할 설계 피드백 항목

중요한 결정은 필요하면 `work-items`에 작업 문서로 남깁니다.
작업 완료 후 현재 기준으로 유지되어야 하는 결정은 적절한 영구 문서로 승격합니다.

## 구현 후 피드백

설계는 구현이 시작된 뒤에도 검증됩니다.
구현 중 다음 신호가 보이면 설계를 다시 봅니다.

- 설계보다 예외 케이스가 많아져 코드가 우회로로 가득 찹니다.
- 하나의 기능 구현을 위해 여러 모듈 내부를 직접 건드립니다.
- 테스트가 느리거나 불안정해 TDD 흐름을 방해합니다.
- 매핑 코드와 boilerplate가 도메인 규칙보다 많아집니다.
- 성능 문제나 N+1 문제가 설계 단계 예상보다 빨리 드러납니다.
- 권한, 상태 전이, 데이터 무결성 규칙이 여러 계층에 흩어집니다.
- 기존 문서와 실제 구현이 달라져 작업자가 구조를 오해합니다.

## 금지 규칙

- 기존 문서에 있다는 이유만으로 설계를 확정하지 않습니다.
- 영향이 큰 설계에서 대안을 생략하지 않습니다.
- "Best Practice"라는 말만으로 결론을 정당화하지 않습니다.
- 사용자의 구현 아이디어를 목표 검토 없이 그대로 따르지 않습니다.
- 설계 리스크를 숨기거나 나중 문제로 미루지 않습니다.
- 기술적 취향이나 익숙함을 제품 목표보다 우선하지 않습니다.
- 설계 검증을 하지 않은 상태에서 확정적인 표현을 사용하지 않습니다.
