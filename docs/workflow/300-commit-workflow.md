# 커밋 워크플로우

이 문서는 커밋을 만들 때의 기준과 절차를 정의합니다.

## 목적

- 커밋을 하나의 명확한 목적 단위로 유지합니다.
- 사용자의 다른 변경 사항이 의도치 않게 커밋에 포함되지 않게 합니다.
- 이후 변경 이력을 읽는 사람이 의도를 빠르게 이해할 수 있게 합니다.

## 기본 원칙

- 사용자가 명시적으로 요청하지 않으면 커밋하지 않습니다.
- 커밋은 기능 또는 의미 있는 변경의 최소 완결 단위로 만듭니다.
- 관련 없는 파일 변경을 같은 커밋에 섞지 않습니다.
- 커밋 전에는 `git status`와 변경 diff를 확인합니다.
- 테스트나 검증을 실행했다면 커밋 전 상태 기준으로 결과를 확인합니다.
- 커밋 작성자는 현재 Git 사용자 설정을 따르고, 공동 작성자 footer는 추가하지 않습니다.

## 커밋 전 체크리스트

- 커밋할 변경이 사용자의 요청 범위에 포함됩니다.
- 사용자가 만든 별도 변경 사항을 포함하지 않습니다.
- 변경 파일과 diff를 확인했습니다.
- 가능한 검증을 실행했고 결과를 확인했습니다.
- 커밋 메시지가 변경 의도를 설명합니다.

## 커밋 메시지 형식

커밋 메시지는 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)을 기본 기준으로 사용합니다.
기본 형식은 다음과 같습니다.

```text
<type>[optional-scope]: <summary>
```

커밋 메시지는 한 줄 요약을 기본으로 합니다.
본문은 변경 이유, 마이그레이션, 호환성 깨짐, 운영상 주의점처럼 제목만으로 부족한 경우에만 사용합니다.
커밋 메시지만으로 대략적인 변경 내용을 파악할 수 있어야 합니다.

권장 타입은 다음과 같습니다.

- `feat`: 기능 추가 또는 사용자 관점의 동작 추가
- `fix`: 버그 수정
- `docs`: 문서 변경
- `style`: 코드 동작과 무관한 포맷 또는 스타일 변경
- `refactor`: 동작 변경 없는 구조 개선
- `perf`: 성능 개선
- `test`: 테스트 추가 또는 수정
- `build`: 빌드 시스템 또는 의존성 변경
- `ci`: CI 설정 또는 파이프라인 변경
- `chore`: 빌드, 설정, 기타 유지보수 작업

`scope`는 변경 영역을 이해하는 데 도움이 될 때만 사용합니다.
억지로 모든 커밋에 붙이지 않습니다.

## 메시지 예시

```text
docs: add commit workflow
```

```text
fix: handle missing car profile image
```

```text
feat(auth): add login endpoint
```

```text
refactor(user): simplify profile lookup
```

## 커밋 단위 예시

- 문서 구조 초안 추가
- 로그인 실패 처리 수정
- 차량 게시글 검색 조건 추가
- 테스트 전용 설정 정리

서로 다른 목적의 변경은 별도 커밋으로 분리합니다.
한 커밋이 여러 타입에 걸치면 가능한 한 커밋을 나눕니다.

## 공동 작성자 원칙

- `Co-authored-by` footer는 사용하지 않습니다.
- 커밋 author는 현재 Git 사용자 설정을 기준으로 합니다.
- 커밋 author를 임의로 바꾸지 않습니다.
