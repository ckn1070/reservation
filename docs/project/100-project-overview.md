# 프로젝트 개요

이 문서는 reservation 프로젝트의 현재 목표, 단계, 확인된 전제와 확인이 필요한 사항을 정리합니다.

## 목적

- 프로젝트의 제품적 배경과 현재 단계를 한곳에서 확인합니다.
- 설계 원칙 문서에 프로젝트 고유 내용을 섞지 않게 합니다.
- 확인된 사실과 아직 확인이 필요한 내용을 구분합니다.

## 현재 목표

reservation은 공연/이벤트 좌석 예약을 위한 Spring Boot 기반 백엔드입니다.
인기 공연 예매처럼 같은 좌석에 동시 요청이 몰리는 상황에서 좌석 단위 데이터 무결성을 지키는 것을 핵심 목표로 합니다.

현재 확인된 목표는 다음과 같습니다.

- 공연장, 층, 열, 좌석을 계층형 리소스로 관리합니다.
- 공연 회차별 좌석 슬롯을 만들고 좌석 상태를 관리합니다.
- 결제 전 좌석 임시 점유와 결제 후 예약 확정을 분리합니다.
- DB 제약과 애플리케이션 검증을 함께 사용해 같은 좌석의 중복 점유를 막습니다.
- 예약, 좌석 잠금, 잠금 이력을 분리해 상태 변화와 감사 흐름을 추적합니다.

## 현재 단계

- 백엔드 핵심 기능이 구현되어 있습니다.
- 회원, 카탈로그, 예약 기능의 컨트롤러, 유스케이스, 도메인, persistence 코드가 존재합니다.
- Flyway migration으로 MySQL 스키마를 관리합니다.
- 문서는 현재 기준 문서와 작업 산출물을 분리하는 구조로 관리합니다.

## 확인된 설계 방향

- bounded context별 기능 우선 패키지 구조를 사용합니다.
- 코드 의존성은 Clean Architecture를 지향합니다.
- 도메인과 유스케이스는 Web, DB, Security 같은 외부 기술 의존성을 피합니다.
- context 간 협력은 직접 내부 구현 참조가 아니라 필요한 Port와 모델로 제한합니다.
- reservation 고유 아키텍처 결정은 `project` 문서에, 일반 원칙과 판단 기준은 `architecture` 문서에 둡니다.

## 확인 필요 사항

다음 내용은 코드와 기존 문서에서 확정 근거를 확인하지 못했습니다.
추측으로 채우지 않고 기능 설계 또는 작업 문서에서 사용자 확인을 받아야 합니다.

- 결제 연동 여부와 결제 실패/취소 정책
- 관리자 운영 도구의 상세 범위
- 예매 오픈 대기열, 알림, 좌석 추천 같은 부가 기능의 우선순위
- 운영 배포 환경, 로그/모니터링, 장애 대응 기준
- 목표 트래픽과 성능 목표
- 개인정보 보존, 회원 탈퇴, 계정 삭제/익명화 정책
- Swagger UI 운영 노출 여부와 관리자 접근 정책
