# 아키텍처 결정 가이드

이 문서는 아키텍처 선택지가 여러 개일 때 대안을 비교하고 결정하는 방식을 정의합니다.

## 목적

- 명확한 선택지는 빠르게 결정합니다.
- 명확하지 않은 선택지는 기준을 세워 비교합니다.
- 결정 이유와 예외 조건을 남겨 이후 유지보수 비용을 줄입니다.

## 결정 절차

1. 목표를 한 문장으로 정리합니다.
2. 변경 대상의 책임 경계를 확인합니다.
3. 관련 문서와 기존 코드를 확인합니다.
4. 가능한 선택지를 2~3개로 압축합니다.
5. 평가 축을 기준으로 장단점을 비교합니다.
6. 권장안을 선택하고 이유를 설명합니다.
7. 예외와 나중에 재검토할 조건을 남깁니다.

## 비교 표 형식

```md
## 선택지

| 선택지 | 장점 | 단점 | 적합한 경우 |
| --- | --- | --- | --- |
| A | | | |
| B | | | |

## 판단

- 추천: A
- 이유:
- 리스크:
- 재검토 조건:
```

## 주요 결정 질문

작업 전 다음 질문에 답합니다.

- 이 로직은 도메인 규칙인가, 애플리케이션 흐름인가, 기술 어댑터인가.
- 변경 가능성이 높은 부분은 어디인가.
- 테스트를 Spring Context 없이 할 수 있어야 하는가.
- 외부 시스템 실패가 핵심 로직에 영향을 주는가.
- DB 모델과 도메인 모델이 같은 언어를 쓰고 있는가.
- 성능 병목이 예상인지, 측정된 사실인지 구분했는가.

## 자주 나오는 선택지

### Entity와 Domain을 분리할지

분리 우위:

- 도메인 규칙이 커집니다.
- JPA 연관관계가 도메인 의도를 흐립니다.
- 순수 단위 테스트가 중요합니다.

통합 우위:

- 단순 CRUD입니다.
- 매핑 코드가 규칙보다 많습니다.
- 초기 탐색 단계입니다.

### UseCase를 둘지

UseCase 우위:

- 여러 Repository/외부 시스템을 조합합니다.
- 권한, 트랜잭션, 도메인 규칙이 있습니다.
- 테스트로 동작을 고정해야 합니다.

단순 Service 우위:

- 단일 Entity 저장/조회가 대부분입니다.
- 도메인 규칙이 아직 없습니다.
- 요구사항 탐색이 먼저입니다.

### Port를 둘지

Port 우위:

- 외부 의존성을 테스트에서 대체해야 합니다.
- DB/외부 API 구현이 바뀔 수 있습니다.
- Application이 기술 세부사항을 알면 안 됩니다.

직접 사용 우위:

- 아주 얇은 CRUD입니다.
- 추상화가 실제 변경 가능성을 줄이지 못합니다.
- 프로젝트 초기이고 경계가 아직 불명확합니다.

### Projection을 사용할지

Projection 우위:

- 목록/검색 조회에서 필요한 필드가 적습니다.
- N+1 또는 과도한 Entity 로딩이 우려됩니다.
- 응답 전용 Read Model이 필요합니다.

Domain 변환 우위:

- 조회 결과에 도메인 정책이 적용됩니다.
- 응답이 복잡한 규칙을 거쳐야 합니다.
- 변경 로직과 동일한 모델 일관성이 중요합니다.

```md
이해한 목표:

선택지:

추천:

이유:

트레이드오프:

확인할 점:
```

## 재검토 조건

다음 조건이 생기면 기존 결정을 다시 봅니다.

- 기능 수가 늘어나 패키지 응집도가 떨어집니다.
- 테스트가 느려져 TDD 흐름을 방해합니다.
- 매핑 코드가 과도하게 반복됩니다.
- JPA 쿼리 성능 문제가 반복됩니다.
- 인증/인가 정책이 여러 계층에 흩어집니다.
- 도메인 용어가 Entity와 API DTO에만 존재합니다.
