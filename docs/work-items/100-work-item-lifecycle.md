# 작업 산출물 생명주기

이 문서는 기능, 버그, 개선, spike 작업 문서를 어떻게 만들고 관리할지 정의합니다.

## 목적

- 작업 과정에서 생기는 맥락과 의사결정을 보존합니다.
- 작업 기록과 현재 기준 문서가 섞이지 않게 합니다.
- 완료된 작업에서 장기 지식을 적절한 영구 문서로 승격합니다.

## 작업 문서 종류

| 종류 | 위치 | 용도 |
| --- | --- | --- |
| 기능 | `features` | 신규 기능 기획, 설계, 개발 계획, 검증 결과 |
| 버그 | `bugs` | 버그 리포트, 재현 절차, 원인 분석, 수정 계획 |
| 개선 | `improvements` | 기존 기능 보완, 성능 개선, 구조 개선 |
| Spike | `spikes` | 기술 가능성 확인, 대안 비교, 실험 결과 |

## 상태 값

작업 문서는 다음 상태를 사용합니다.

- `Proposed`: 제안됨
- `Planned`: 진행하기로 계획됨
- `In Progress`: 진행 중
- `Done`: 완료됨
- `Superseded`: 다른 작업이나 결정으로 대체됨
- `Rejected`: 진행하지 않기로 결정됨

## 작성 절차

1. 작업 종류를 고릅니다.
2. 해당 디렉터리의 템플릿을 사용해 문서를 만듭니다.
3. 배경, 목표, 범위, 제외 범위를 먼저 작성합니다.
4. 필요한 설계, 개발 계획, 검증 계획을 작성합니다.
5. 작업 중 발생한 중요한 판단과 변경 사항을 기록합니다.
6. 완료 후 결과와 검증 결과를 정리합니다.
7. 장기 지식으로 남길 내용을 관련 영구 문서로 승격합니다.
8. 승격한 문서 링크를 작업 문서에 남깁니다.

## 영구 문서 승격 기준

다음 내용은 작업 문서에만 두지 않고 관련 영구 문서로 옮깁니다.

- 제품 범위나 로드맵에 영향을 주는 결정
- 도메인 용어, 업무 규칙, 상태 전이
- API 엔드포인트, 에러 코드, 인증/인가 계약
- DB 스키마, 제약조건, migration 작성 기준
- 모듈 경계와 아키텍처 결정
- 기술 스택 사용 기준 변경
- 반복될 가능성이 큰 작업 절차
- 운영 정책, 보안 정책, 데이터 보존 정책

승격 위치는 다음 기준을 따릅니다.

- 제품 범위와 정책: `product`
- 도메인 지식과 규칙: `domain`
- API 계약: `api`
- DB 구조와 migration 기준: `database`
- 현재 프로젝트 구조와 결정: `project`
- 아키텍처 원칙과 방법: `architecture`
- 기술별 사용 기준: `tech-stack`
- 작업 방식: `workflow`

## 보존 기준

- 완료된 작업 문서는 삭제하지 않습니다.
- 잘못된 시도도 이후 판단에 도움이 되면 남깁니다.
- 오래된 작업 문서가 현재 기준과 다르면 문서 상단이나 결과 섹션에 현재 기준 문서 링크를 추가합니다.
- 작업 문서는 현재 기준이 아니라 당시의 맥락과 이력을 보존하는 자료로 봅니다.
