# 문서 작성 가이드

이 문서는 프로젝트 문서를 작성하고 유지보수하는 공통 규칙을 정의합니다.

## 목적

- 문서가 늘어나도 필요한 정보를 빠르게 찾을 수 있게 합니다.
- 작업자가 같은 기준으로 문서를 작성하고 갱신할 수 있게 합니다.
- 설명 문서, 현재 결정, 작업 기록이 섞여 관리되지 않도록 역할을 분리합니다.

## 기본 원칙

- 문서는 한 페이지 목차와 상세 문서 구조로 확장합니다.
- 목차 문서는 길게 설명하지 않고, 문서의 목적과 읽는 순서를 안내합니다.
- 상세 문서는 목적, 적용 범위, 판단 기준, 실행 절차, 체크리스트를 우선 포함합니다.
- 오래 유지될 규칙과 일회성 메모를 구분합니다.
- 문서는 코드와 함께 유지보수되어야 합니다.
- 문서를 작성하기 전에 문서 그룹의 전체 구조를 먼저 파악합니다.
- 기존 문서 구조 개편이 불가피하면 문서를 작성하기 전에 개편이 필요한 이유를 사용자에게 먼저 제시합니다.
- 확인할 수 없는 내용을 추측으로 채우지 않고 사용자 확인을 받거나 확인 필요 사항으로 남깁니다.

## 문서 작성 절차

문서를 새로 작성하거나 의미 있게 갱신할 때는 다음 순서를 따릅니다.

1. `docs/000-index.md`에서 전체 문서 지도를 확인합니다.
2. 관련 문서 그룹의 `000-index.md`를 확인합니다.
3. 기존 문서와 새 문서가 중복되거나 충돌하는지 확인합니다.
4. 전체 구조 개편이 필요한지 판단합니다.
5. 구조 개편이 필요하면 개편 이유, 영향 범위, 대안을 사용자에게 먼저 제시합니다.
6. 구조 개편 없이 진행할 수 있으면 문서 위치와 파일명을 결정합니다.
7. 문서의 목차와 섹션 구조를 먼저 설계합니다.
8. 각 섹션에 구체적인 설명, 판단 기준, 예시, 예외 조건을 채웁니다.
9. 직접 확인할 수 없는 사실, 정책, 도메인 지식은 확인 필요 사항으로 남깁니다.
10. 관련 `000-index.md`, 관련 문서 링크, 변경 로그를 갱신합니다.

## 문서 구조 원칙

- 문서는 사용자가 한눈에 전체 구조를 파악한 뒤 상세 내용을 확인할 수 있어야 합니다.
- 개념 설명 문서는 용어 정의, 적용 여부, 적용 기준, 예외 기준을 분리합니다.
- 작업 규칙 문서는 목적, 적용 범위, 절차, 체크리스트, 중단 조건을 포함합니다.
- 설계 문서는 목표, 대안, 선택 이유, 트레이드오프, 리스크, 재검토 조건을 포함합니다.
- 설명은 내용을 모르는 사람이 읽어도 이해할 수 있을 만큼 구체적으로 작성합니다.
- 추상적인 원칙만 적지 않고, 프로젝트에서 어떤 판단으로 이어지는지 함께 적습니다.
- 같은 단어를 서로 다른 의미로 쓰지 않습니다.
- 용어가 혼동될 수 있으면 먼저 정의하고 이후 같은 의미로만 사용합니다.

## 문서 유형과 위치

문서는 성격에 따라 위치를 분리합니다.
원칙, 현재 결정, 도메인 지식, 제품 기획, API 계약, DB 구조, 작업 기록을 같은 문서에 섞지 않습니다.

| 문서 그룹 | 역할 | 넣는 내용 | 넣지 않는 내용 |
| --- | --- | --- | --- |
| `workflow` | 작업 방식과 절차 | 설계, 개발, TDD, 커밋 같은 작업 흐름 | 특정 기능의 실제 작업 기록 |
| `architecture` | 아키텍처 원칙과 방법 | Clean Architecture, Ports and Adapters, 패키지 구조, 경계와 매핑 기준 | 실제 프로젝트 모듈 목록, 기능 범위 |
| `tech-stack` | 기술별 사용 기준 | Java, Spring, JPA, Flyway, MySQL, OpenAPI 사용 원칙 | 특정 기능 구현 계획 |
| `project` | 현재 프로젝트 결정 상태 | 현재 아키텍처 선택, 모듈 지도, 실행과 설정 | 일반 아키텍처 개념 설명 |
| `product` | 제품 방향과 기획 | 제품 목표, 사용자 범위, MVP, 기능 범위, 보류 범위 | 구현 상세와 코드 구조 |
| `domain` | 업무 지식과 도메인 규칙 | 도메인 용어, 모델 의미, 정책, 상태 전이, 비즈니스 흐름 | 작업 진행 로그 |
| `api` | HTTP API 계약 요약 | 엔드포인트, 에러 코드, 인증 전제 | 도메인 정책의 원문 |
| `database` | DB 구조와 migration 기준 | 테이블, 제약조건, 상태 컬럼, Flyway 주의사항 | 기능 작업 계획 |
| `work-items` | 작업 산출물과 이력 | 기능/버그/개선/spike의 배경, 계획, 진행, 결과 | 현재 기준으로 유지되어야 할 최종 지식 |

### 원칙 문서와 프로젝트 문서 분리

- 원칙 문서는 오래 유지되는 방법과 판단 기준을 다룹니다.
- 프로젝트 문서는 현재 reservation에 적용한 구체적인 결정을 다룹니다.
- 원칙 문서에는 프로젝트 고유 내용을 결정처럼 쓰지 않습니다.
- 원칙 설명에 예시가 필요하면 예시임을 분명히 하고, 실제 결정은 `project`, `product`, `domain` 문서에 둡니다.

### 작업 산출물과 영구 문서 분리

- `work-items`는 작업의 역사와 맥락을 보존합니다.
- `project`, `product`, `domain`, `api`, `database`, `architecture`, `tech-stack`은 현재 기준을 보존합니다.
- 작업 중 생긴 장기 지식은 완료 후 적절한 영구 문서로 승격합니다.
- 승격 후에도 원래 작업 문서는 삭제하지 않고, 관련 문서 링크를 남깁니다.
- 평소에는 현재 기준 문서를 먼저 읽고, 이유와 맥락이 필요할 때 작업 산출물을 추적합니다.

## 네이밍 규칙

- 각 문서 그룹의 목차 파일은 `000-index.md`를 사용합니다.
- 큰 분류 문서는 `100-topic-name.md`, `200-topic-name.md`처럼 100 단위 번호를 사용합니다.
- 세부 문서는 `210-topic-name.md`, `220-topic-name.md`처럼 같은 큰 분류 안의 10 단위 번호를 사용합니다.
- 파일명은 기본적으로 영문 소문자와 하이픈을 사용합니다.
- 문서 제목은 한국어로 작성할 수 있습니다.
- 번호는 작성 순서가 아니라 읽기 순서와 개념 계층을 나타냅니다.
- `000`은 목차, `100/200/300`은 큰 분류, `110/210/220`은 세부 문서에 사용합니다.
- 번호 체계는 각 디렉터리 안에서 독립적으로 적용합니다.
- 같은 번호는 서로 다른 문서 그룹에서 반복될 수 있습니다. 예: `workflow/200-*`, `architecture/200-*`, `tech-stack/200-*`.
- 같은 디렉터리 안에서는 같은 번호를 중복해서 사용하지 않습니다.
- 문서 사이에 새 문서를 삽입해야 하면 비어 있는 중간 번호를 사용합니다.

## 권장 문서 구조

```md
# 문서 제목

## 목적

## 적용 범위

## 핵심 원칙

## 작업 절차

## 체크리스트

## 관련 문서

## 변경 로그
```

모든 문서가 이 구조를 반드시 따라야 하는 것은 아닙니다.
다만 작업 규칙이나 워크플로우 문서는 이 구조를 기본값으로 사용합니다.

## 목차 문서 작성 규칙

- 해당 문서 그룹의 목적을 먼저 설명합니다.
- 상세 문서 목록에는 각 문서의 역할을 한 줄로 적습니다.
- 권장 읽기 순서가 있으면 명시합니다.
- 아직 작성되지 않았지만 예정된 문서는 별도 섹션으로 분리합니다.

## 문서 갱신 기준

- 같은 설명을 두 번 이상 반복하게 되면 문서화를 검토합니다.
- 작업 방식이 바뀌면 관련 워크플로우 문서를 갱신합니다.
- 코드 구조가 바뀌면 관련 아키텍처 문서를 갱신합니다.
- 규칙이 실제 작업과 맞지 않으면 규칙을 유지할지, 수정할지 먼저 판단합니다.
- 새 문서가 기존 문서의 규칙을 대체하면 기존 문서의 충돌 내용을 함께 갱신합니다.
- 문서 이름이나 위치가 새 기준과 맞지 않으면 링크 갱신과 함께 이름 변경을 검토합니다.

## 사용자 확인 기준

다음 내용은 저장소, 코드, 기존 문서, 사용자 합의에서 확인할 수 없으면 추측하지 않고 사용자에게 확인하거나 확인 필요 사항으로 남깁니다.

- 제품 목표, 사용자 범위, 수익화, 운영 정책
- 도메인 용어의 정확한 의미와 업무 규칙
- 법적, 보안, 개인정보, 결제, 운영 리스크가 있는 정책
- 외부 서비스 사용 여부, 비용 제약, 배포 환경
- 성능 목표, 트래픽 가정, 데이터 보존 기간
- 기존 문서와 더 나은 설계 방향이 충돌할 때의 우선순위
- 대안의 장단점이 비슷해 기술 판단만으로 결정하기 어려운 선택

## 변경 로그 규칙

- 각 문서는 하단에 `변경 로그` 섹션을 둡니다.
- 문서의 의미, 구조, 규칙이 바뀐 경우에만 기록합니다.
- 오탈자, 표현 정리, 단순 링크 수정처럼 의미 변화가 없는 변경은 기록하지 않습니다.
- 최신 변경 사항을 위에 둡니다.
- 각 날짜 아래에는 중요한 변경만 1~3줄 정도로 남깁니다.

## 문서 추가 체크리스트

- 새 문서가 기존 문서와 중복되지 않는지 확인했습니다.
- 적절한 디렉터리와 번호를 선택했습니다.
- 문서 유형이 `workflow`, `architecture`, `tech-stack`, `project`, `product`, `domain`, `api`, `database`, `work-items` 중 어디에 속하는지 확인했습니다.
- 관련 `000-index.md`에 링크를 추가했습니다.
- 문서의 목적과 적용 범위를 명확히 적었습니다.
- 추후 갱신이 필요한 조건을 드러냈습니다.
- 문서 구조를 먼저 잡고 설명을 채웠습니다.
- 확인할 수 없는 내용은 추측하지 않고 확인 항목으로 남겼습니다.
- 기존 문서와 충돌하는 내용이 있으면 함께 갱신했습니다.
